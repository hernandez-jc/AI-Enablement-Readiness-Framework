# 06 — Tecnología e infraestructura

> **Dimensión del framework:** Tecnología, arquitectura e infraestructura
> **Pregunta central:** ¿La organización dispone de las herramientas, infraestructura, integraciones y capacidades técnicas necesarias para implementar y operar los casos de uso de IA de manera sostenible?

## 1. ¿Por qué importa?

Una organización puede tener:

- casos de uso atractivos;
- datos disponibles;
- personas capacitadas;
- apoyo ejecutivo;

y aun así no estar preparada para implementar IA si su entorno tecnológico no puede soportar las soluciones requeridas.

La preparación tecnológica incluye mucho más que disponer de acceso a una herramienta de IA.

También implica evaluar:

- infraestructura;
- arquitectura;
- aplicaciones;
- integración;
- conectividad;
- almacenamiento;
- seguridad;
- gestión de identidades y accesos;
- interoperabilidad;
- capacidad de procesamiento;
- disponibilidad;
- escalabilidad;
- soporte técnico;
- gestión del ciclo de vida.

Por eso, la pregunta no es:

> "¿Tenemos acceso a herramientas de IA?"

Sino:

> **"¿Nuestra arquitectura tecnológica puede soportar de manera segura, integrada y sostenible los casos de uso de IA que queremos implementar?"**

---


# 2. El principio de "tecnología al servicio del caso de uso"

No todos los casos de uso requieren la misma infraestructura.

Una aplicación sencilla para asistir a usuarios puede requerir capacidades muy diferentes de un sistema de IA integrado directamente en procesos operativos críticos.

| Tipo de caso de uso                    | Necesidades tecnológicas principales                     |
| -------------------------------------- | -------------------------------------------------------- |
| Asistencia individual                  | Herramienta autorizada, acceso y conectividad            |
| Generación de contenido                | Herramienta, almacenamiento y controles de acceso        |
| Consulta sobre información interna     | Integración con fuentes de información                   |
| Automatización de procesos             | Integración, APIs, flujos de trabajo y monitoreo         |
| Análisis avanzado                      | Datos, procesamiento y capacidades analíticas            |
| Sistema integrado en operación crítica | Arquitectura robusta, seguridad, monitoreo y continuidad |

Por lo tanto:

> **La madurez tecnológica debe evaluarse en relación con las necesidades del caso de uso.**

# 4. TECH-01 — Herramientas disponibles
## Qué significa

Evalúa si la organización dispone de herramientas de IA apropiadas y autorizadas para los casos de uso prioritarios.

Esto incluye analizar:

- funcionalidades;
- compatibilidad;
- seguridad;
- facilidad de uso;
- integración;
- costos;
- condiciones de utilización;
- soporte.
## ¿Por qué importa?

Tener muchas herramientas no significa tener una arquitectura tecnológica preparada.

Una proliferación descontrolada de herramientas puede generar:

- duplicación;
- costos innecesarios;
- riesgos de seguridad;
- fragmentación;
- dificultades de soporte;
- problemas de integración.

## Conexión con el assessment

Una puntuación baja puede indicar que la organización necesita:

- seleccionar herramientas;
- consolidar plataformas;
- definir estándares;
- evaluar alternativas;
- establecer procesos de aprobación.

---


# 5. TECH-02 — Infraestructura
## Qué significa

Evalúa si la infraestructura tecnológica puede soportar las necesidades del caso de uso.

Puede incluir:

- capacidad de procesamiento;
- almacenamiento;
- conectividad;
- disponibilidad;
- capacidad de cómputo;
- servicios en la nube;
- sistemas locales;
- capacidad de respaldo.
## ¿Por qué importa?

Una solución puede funcionar correctamente en una prueba pequeña y presentar problemas cuando aumenta:

- el número de usuarios;
- el volumen de datos;
- la frecuencia de utilización;
- la complejidad de las tareas.

Por eso, debe distinguirse entre:

> **capacidad para experimentar**
y

> **capacidad para operar a escala.**


---


# 6. TECH-03 — Arquitectura tecnológica
## Qué significa

Evalúa si la arquitectura existente puede incorporar IA sin generar una dependencia insostenible o una complejidad excesiva.

La evaluación puede considerar:

- sistemas existentes;
- aplicaciones;
- bases de datos;
- servicios;
- infraestructura;
- integraciones;
- seguridad;
- flujos de información.
## ¿Por qué importa?

Una solución aislada puede funcionar como piloto, pero resultar difícil de mantener cuando se integra al entorno empresarial.

## Pregunta clave

> **¿La solución puede incorporarse a la arquitectura existente de manera sostenible?**

---


# 7. TECH-04 — Integración
## Qué significa

Evalúa si las soluciones de IA pueden conectarse con las aplicaciones y procesos existentes.

La integración puede ser necesaria para:

- acceder a información;
- enviar resultados;
- iniciar procesos;
- actualizar registros;
- automatizar tareas;
- proporcionar contexto a la IA.
## ¿Por qué importa?

Muchas oportunidades de IA dependen de que el sistema pueda interactuar con el entorno donde realmente ocurre el trabajo.

Una herramienta aislada puede ser útil para productividad individual, pero insuficiente para automatizar un proceso completo.

## Conexión con procesos

Aquí aparece una relación directa:

> **Tecnología + proceso**

Una integración técnicamente posible no necesariamente produce una mejora de proceso.

---


# 8. TECH-05 — APIs e interoperabilidad
## Concepto clave: API

Una API permite que diferentes sistemas intercambien información y funciones de manera estructurada.

## ¿Por qué importa?

Las APIs pueden facilitar la integración de IA con:

- aplicaciones;
- plataformas;
- bases de datos;
- sistemas internos;
- herramientas empresariales;
- flujos automatizados.
## Conexión con el assessment

Una puntuación baja puede indicar que la arquitectura actual dificulta:

- automatización;
- intercambio de información;
- integración;
- escalamiento.

En estos casos, la brecha puede ser principalmente tecnológica y no de aprendizaje.

--


# 9. TECH-06 — Seguridad técnica
## Qué significa

Evalúa si existen controles tecnológicos adecuados para proteger sistemas y datos utilizados por soluciones de IA.

Puede incluir:

- autenticación;
- autorización;
- cifrado;
- aislamiento;
- monitoreo;
- gestión de vulnerabilidades;
- protección de interfaces;
- gestión de secretos;
- controles sobre aplicaciones.
## ¿Por qué importa?

La incorporación de IA puede crear nuevos puntos de interacción entre:

**usuarios + datos + aplicaciones + servicios externos.**

Estos puntos deben considerarse dentro del modelo de seguridad existente.

## Conexión con Gobernanza

La gobernanza establece qué debe protegerse y bajo qué reglas.

La tecnología proporciona parte de los mecanismos para aplicar esos controles.


---


# 10. TECH-07 — Identidad y acceso
## Qué significa

Evalúa si la organización puede controlar quién puede utilizar:

- herramientas;
- modelos;
- aplicaciones;
- datos;
- funciones específicas.

También considera si los permisos pueden ajustarse al rol y al contexto.

## ¿Por qué importa?

No todos los usuarios deben necesariamente tener:

- el mismo acceso;
- las mismas capacidades;
- acceso a los mismos datos;
- capacidad para modificar los mismos sistemas.

## Conexión con Skills

Los usuarios necesitan comprender sus responsabilidades.

Pero los controles tecnológicos deben respaldar ese comportamiento.

Por eso:

> **La seguridad no puede depender exclusivamente de que las personas recuerden las reglas.**

---


# 11. TECH-08 — Escalabilidad y rendimiento
## Qué significa

Evalúa si una solución puede crecer manteniendo un nivel de rendimiento aceptable.

Debe considerarse qué ocurre cuando aumentan:

- usuarios;
- transacciones;
- volumen de datos;
- frecuencia de uso;
- complejidad;
- integraciones.
## ¿Por qué importa?

Una solución que funciona para diez personas puede no funcionar igual para mil.

## Conexión con el assessment

Este criterio ayuda a distinguir entre:

**Proof of Concept → Piloto → Producción → Escala**

Cada etapa puede requerir capacidades tecnológicas diferentes.


---


# 12. TECH-09 — Monitoreo y soporte
## Qué significa

Evalúa si existen mecanismos para conocer el estado de las soluciones y responder cuando ocurren problemas.

El monitoreo puede incluir:

- disponibilidad;
- rendimiento;
- errores;
- uso;
- consumo;
- incidentes;
- cambios;
- comportamiento del sistema.
## ¿Por qué importa?

Una solución de IA en producción se convierte en parte del entorno operativo.

Necesita:

- soporte;
- mantenimiento;
- resolución de incidentes;
- seguimiento;
- responsables.
Conexión con AI Enablement

Los usuarios también necesitan saber:

- cómo reportar problemas;
- cuándo escalar;
- qué tipo de incidentes requieren intervención;
- qué hacer cuando la herramienta no funciona como se espera.

---


# 13. TECH-10 — Continuidad y ciclo de vida
Concepto clave: Technology Lifecycle

Las soluciones tecnológicas no permanecen estáticas.

Una solución puede necesitar:

- actualización;
- modificación;
- migración;
- sustitución;
- suspensión;
- retiro.

El assessment debe determinar si existe capacidad para gestionar estas transiciones.

## Pregunta clave

> **¿Qué ocurre cuando la herramienta cambia, deja de estar disponible o deja de satisfacer las necesidades del negocio?**

Esto es especialmente importante cuando una solución se vuelve crítica para una operación.

# 14. Cómo interpretar el score de Tecnología

La aplicación utiliza una escala de 1 a 5.
| Score | Nivel         | Interpretación                                                                              |
| ----: | ------------- | ------------------------------------------------------------------------------------------- |
|     1 | Inicial       | La capacidad tecnológica es limitada o depende de soluciones aisladas                       |
|     2 | En desarrollo | Existen herramientas y capacidades parciales                                                |
|     3 | Funcional     | La infraestructura soporta los principales casos de uso actuales                            |
|     4 | Gestionada    | La arquitectura, integración, seguridad y operación están gestionadas de manera consistente |
|     5 | Optimizada    | La plataforma tecnológica es escalable, integrada, monitoreada y mejora continuamente       |

El resultado debe interpretarse en función de los casos de uso prioritarios.

# 15. Tecnología disponible no significa preparación tecnológica

Una organización puede tener acceso a herramientas avanzadas y aun así presentar una preparación tecnológica limitada.
El resultado debe interpretarse en función de los casos de uso prioritarios.

La evaluación debe centrarse en la **capacidad de utilizar la tecnología para producir resultados sostenibles.**

# 16. Del assessment al Training Needs Analysis

Una brecha tecnológica no debe convertirse automáticamente en una necesidad de capacitación.

Primero debe identificarse la causa.
| Situación                                        | Tipo de brecha             | Posible intervención        |
| ------------------------------------------------ | -------------------------- | --------------------------- |
| Usuarios no saben utilizar la herramienta        | Skills                     | Formación                   |
| Usuarios no conocen herramientas autorizadas     | Conocimiento               | Orientación / capacitación  |
| No existe integración                            | Tecnología                 | Desarrollo / arquitectura   |
| Sistemas incompatibles                           | Tecnología                 | Modernización / integración |
| No existen controles de acceso                   | Tecnología / seguridad     | Implementación técnica      |
| La herramienta está disponible pero no se adopta | Skills / proceso / cultura | Intervención combinada      |
| No existe soporte                                | Operación                  | Modelo de soporte           |

Esto evita utilizar capacitación para resolver problemas que requieren cambios tecnológicos.

20. Tecnología y experiencia del usuario

La preparación tecnológica también afecta la experiencia de las personas.

Una herramienta puede ser técnicamente excelente y producir baja adopción si:

- es difícil de utilizar;
- requiere demasiados pasos;
- no está integrada con las herramientas habituales;
- genera resultados difíciles de incorporar al trabajo;
- tiene tiempos de respuesta deficientes;
- requiere conocimientos técnicos innecesarios.

Por eso, la evaluación debe considerar:

> **¿La tecnología facilita realmente el trabajo que queremos transformar?**

21. Tecnología y cambio de procesos

Una solución de IA rara vez debe analizarse exclusivamente como una nueva aplicación.

Puede modificar el flujo de trabajo.

Por ejemplo:

Proceso actual
      ↓
Tarea manual
      ↓
Revisión
      ↓
Aprobación
      ↓
Resultado
Proceso actual
      ↓
Tarea manual
      ↓
Revisión
      ↓
Aprobación
      ↓
Resultado

puede convertirse en:

Proceso con IA
      ↓
Preparación de información
      ↓
Asistencia de IA
      ↓
Validación humana
      ↓
Corrección / decisión
      ↓
Resultado
      ↓
Registro

La arquitectura tecnológica debe soportar este nuevo flujo.

Pero también deben definirse:

- responsabilidades;
- controles;
- habilidades;
- criterios de calidad.

---


# 22. Tecnología como habilitador, no como fin

El objetivo de esta dimensión no es determinar si la organización tiene la tecnología más avanzada.

Es determinar si dispone de la tecnología adecuada para sus necesidades.

Una solución más sofisticada no necesariamente es una solución mejor.

La evaluación debe considerar:

> **Adecuación + seguridad + integración + sostenibilidad + costo + capacidad de escala**

# 24. Indicadores complementarios



Los resultados del assessment pueden complementarse con indicadores como:

- porcentaje de herramientas de IA autorizadas;
- número de herramientas duplicadas;
- porcentaje de casos de uso integrados con sistemas existentes;
- disponibilidad de APIs;
- tiempo promedio de integración;
- disponibilidad de servicios;
- número de incidentes tecnológicos;
- tiempo de resolución;
- porcentaje de soluciones con monitoreo;
- porcentaje de soluciones con responsable técnico;
- capacidad utilizada frente a capacidad disponible;
- porcentaje de soluciones escaladas desde piloto a producción.

Estos indicadores ayudan a observar la evolución de la preparación tecnológica.

#  25. Conexión con las demás dimensiones

La tecnología depende de las otras dimensiones del framework.

Dimensión	Relación con tecnología
Datos	Determina qué información puede utilizarse y cómo integrarla
Skills	Determina si las personas pueden utilizar y operar las herramientas
Gobernanza	Define reglas, responsabilidades y controles
Estrategia	Define qué capacidades tecnológicas son prioritarias
Procesos	Determina dónde y cómo se incorporará la tecnología
Cultura	Influye en la adopción y utilización efectiva
Medición	Permite comprobar el rendimiento y valor de la solución

Por eso:

> **La tecnología no debe evaluarse como una dimensión aislada.**

Debe evaluarse como parte del sistema que permite convertir una oportunidad de negocio en un resultado operativo.

# 26. Del assessment al plan de acción

Las brechas tecnológicas pueden convertirse en acciones concretas.

Brecha	Acción	Responsable	Indicador
Herramientas fragmentadas	Consolidar plataformas	Tecnología	Número de plataformas
Falta de integración	Diseñar integración	Arquitectura	Integraciones implementadas
Acceso inadecuado	Revisar permisos	Seguridad	Accesos correctamente configurados
Falta de monitoreo	Implementar monitoreo	Operaciones	Soluciones monitoreadas
Baja capacidad	Ampliar infraestructura	Tecnología	Capacidad disponible
Falta de conocimientos	Desarrollar habilidades	Learning / Tecnología	Competencias demostradas

Esta estructura conecta el diagnóstico tecnológico con el plan de transformación.

#  27. Idea clave para el workshop

**💡 La preparación tecnológica no significa tener más tecnología. Significa tener la tecnología adecuada para ejecutar los casos de uso prioritarios de manera segura, integrada y sostenible.**

La evaluación debe permitir responder:


¿Qué queremos lograr?
↓
¿Qué solución necesitamos?
↓
¿Qué tecnología requiere?
↓
¿Puede integrarse con nuestro entorno?
↓
¿Puede operarse y escalarse?
↓
¿Qué capacidades técnicas y humanas necesitamos?
↓
¿Cómo mediremos su desempeño?


El objetivo final no es alcanzar una determinada tecnología.

Es construir la capacidad organizacional necesaria para que:

> **la estrategia pueda ejecutarse → los casos de uso puedan implementarse → las personas puedan utilizarlos → los controles puedan funcionar → y los resultados puedan sostenerse a escala.**
